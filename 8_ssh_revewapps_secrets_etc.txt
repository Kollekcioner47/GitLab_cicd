Практика 8: Полноцикловый проект с нуля — CRM, деплой на целевой сервер, Review Apps и секреты

В этой практике мы создадим проект с нуля, чтобы освежить навыки работы с Git, и реализуем многоконтейнерное приложение: простую CRM-систему. 

Архитектура приложения:
1. PostgreSQL — база данных для хранения клиентов и сделок.
2. Backend (Бизнес-логика) — REST API на Python (FastAPI), которое работает с БД.
3. Frontend (CRM UI) — Веб-интерфейс на Python, который отдаёт HTML и обращается к Backend.

Чему мы научимся:
- Создавать проект в GitLab с нуля.
- Настраивать деплой на удалённый сервер (10.0.2.6) с помощью GitLab Runner, установленного прямо на нём.
- Использовать параллельные тесты и генерировать JUnit-отчеты.
- Создавать временные окружения (Review Apps) для веток.
- Управлять секретами через CI/CD Variables и очищать артефакты.

--- 
Шаг 1. Подготовка удалённого сервера (10.0.2.6)
Деплой выполняет GitLab Runner, установленный на самом сервере `10.0.2.6`: джобы с тегом `app-server` исполняются там и поднимают контейнеры локально, поэтому SSH-ключи для деплоя не нужны — команды просто выполняются на самой целевой машине. На app-server (`10.0.2.6`) выполните:

Установим Docker и Docker Compose
sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin -y
sudo usermod -aG docker $USER

echo "ipv4" | sudo tee /etc/curlrc
curl -s https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh | sudo bash
sudo apt install -y gitlab-runner

sudo -i
visudo
добавляем
gitlab-runner ALL=(ALL) NOPASSWD: ALL
сохраняем
logout

sudo nano /etc/hosts
добавьте:
10.0.2.5	gitlab.local


Выйдите и зайдите снова, чтобы группа применилась

Если вы хотите попробовать классический SSH-деплой вместо раннер-деплоя — это отдельное упражнение: сгенерируйте ключ, положите приватную часть в CI-переменную типа File и вызывайте `ssh -i ... docker compose ...`; в этой практике мы так не делаем.

Дальше две команды на разных машинах: сертификат берём с сервера GitLab (10.0.2.5) и ставим на app-server (10.0.2.6).
Скопируйте сертификат с сервера GitLab (10.0.2.5):
sudo scp /etc/gitlab/ssl/gitlab.local.crt engineer@10.0.2.6:/home/engineer
на app-server (10.0.2.6):
sudo cp ~/gitlab.local.crt /usr/local/share/ca-certificates/gitlab-local.crt
sudo chmod 644 /usr/local/share/ca-certificates/gitlab-local.crt
sudo update-ca-certificates --fresh

Зарегистрируйте раннер — команда выполняется на app-server (10.0.2.6):
sudo gitlab-runner register --url https://gitlab.local --token <ваш_токен_раннера>
имя раннера: app-server
теги: app-server
executor: docker
default image: docker:cli

ВАЖНО: тег нужно указать обязательно — либо в вопросе `Enter tags for the runner` при регистрации, либо позже в UI (**Settings -> CI/CD -> Runners**, отредактировав раннер). Без тега `app-server` деплой-джобы с `tags: [app-server]` никогда не запустятся и будут висеть в статусе pending.

Добавьте монтирование docker.sock и extra_hosts в конфиг раннера
Отредактируйте /etc/gitlab-runner/config.toml:
[[runners]]
  name = "app-server"
  url = "https://gitlab.local"
  token = "ваш_токен"
  executor = "docker"
  [runners.docker]
    image = "docker:cli"
    extra_hosts = ["gitlab.local:10.0.2.5"]   # <--- чтобы внутри контейнера видел GitLab
    privileged = true
    volumes = [
      "/var/run/docker.sock:/var/run/docker.sock",   # <--- чтобы вызывать docker
      "/cache"
    ]

После этого перезапустите раннер:
sudo gitlab-runner restart
Теперь каждый контейнер, запущенный раннером, будет иметь в /etc/hosts запись gitlab.local → 10.0.2.5.

Добавьте сертификат GitLab в доверенные для локального Docker-демона (чтобы он мог пушить образы):

sudo mkdir -p /etc/docker/certs.d/gitlab.local:5050
sudo cp gitlab.local.crt /etc/docker/certs.d/gitlab.local:5050/ca.crt
sudo systemctl restart docker

Шаг 3. Пишем код приложения

Создадим структуру директорий:

**1. База данных (инициализация)**
Создайте файл `db/init.sql`:

CREATE TABLE IF NOT EXISTS deals (
    id SERIAL PRIMARY KEY,
    client_name VARCHAR(100) NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    status VARCHAR(20) DEFAULT 'new'
);


**2. Backend (Бизнес-логика)**
Создайте `backend/app.py`:

import os
from fastapi import FastAPI, Depends
from sqlalchemy import create_engine, Column, Integer, String, Numeric
from sqlalchemy.orm import declarative_base, sessionmaker, Session
from pydantic import BaseModel

DATABASE_URL = os.getenv("DATABASE_URL", "postgresql://crm:secret@db:5432/crmdb")

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()


class Deal(Base):
    __tablename__ = "deals"
    id = Column(Integer, primary_key=True, index=True)
    client_name = Column(String(100), nullable=False)
    amount = Column(Numeric(10, 2), nullable=False)
    status = Column(String(20), default="new")


Base.metadata.create_all(bind=engine)
app = FastAPI(title="CRM Business Logic")


class DealCreate(BaseModel):
    client_name: str
    amount: float


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


@app.get("/api/deals")
def list_deals(db: Session = Depends(get_db)):
    return db.query(Deal).all()


@app.post("/api/deals")
def create_deal(deal: DealCreate, db: Session = Depends(get_db)):
    db_deal = Deal(client_name=deal.client_name, amount=deal.amount)
    db.add(db_deal)
    db.commit()
    db.refresh(db_deal)
    return db_deal

3. Frontend (CRM UI)
Создайте `frontend/app.py`:

import os
import httpx
from fastapi import FastAPI, Request
from fastapi.responses import HTMLResponse

API_URL = os.getenv("API_URL", "http://backend:8000")

app = FastAPI()


@app.get("/", response_class=HTMLResponse)
async def index(request: Request):
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"{API_URL}/api/deals")
        deals = resp.json()
    
    rows = "".join(
        f"<tr><td>{d['id']}</td><td>{d['client_name']}</td>"
        f"<td>{d['amount']}</td><td>{d['status']}</td></tr>"
        for d in deals
    )
    
    return f"""
    <html><head><title>Mini CRM</title></head><body>
    <h1>CRM Deals</h1>
    <table border="1" cellpadding="5">
    <tr><th>ID</th><th>Client</th><th>Amount</th><th>Status</th></tr>
    {rows}
    </table></body></html>
    """

from fastapi.testclient import TestClient
from backend.app import app

client = TestClient(app)


def test_create_deal():
    response = client.post(
        "/api/deals",
        json={"client_name": "Test Corp", "amount": 5000.0}
    )
    assert response.status_code == 200
    data = response.json()
    assert data["client_name"] == "Test Corp"

Шаг 5. Пишем продвинутый CI/CD пайплайн

Создайте файл `.gitlab-ci.yml` в корне проекта. Здесь мы реализуем все запрошенные фичи:


stages:
  - test
  - build
  - deploy

variables:
  DOCKER_TAG: $CI_COMMIT_SHORT_SHA

# Правила для веток
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

# ---------------------------------------------------------
# 1. Тестирование с JUnit и параллельным запуском
# ---------------------------------------------------------
test_backend:
  stage: test
  image: python:3.11-slim
  tags:
    - docker
  services:
    - postgres:15-alpine
  variables:
    POSTGRES_USER: crm
    POSTGRES_PASSWORD: $DB_PASSWORD # Используем секрет!
    POSTGRES_DB: crmdb
    DATABASE_URL: "postgresql://crm:$DB_PASSWORD@postgres:5432/crmdb"
  before_script:
    - apt-get update && apt-get install -y wait-for-it
    - pip install -r backend/requirements.txt pytest 
    - wait-for-it postgres:5432 --timeout=30
  script:
    - export PYTHONPATH=.
    - pytest -v tests/ --junitxml=tests/report-backend.xml
  artifacts:
    when: always
    paths:
      - tests/report-backend.xml
    reports:
      junit: tests/report-backend.xml
    expire_in: 1 day # Очистка артефактов через 1 день


# Вторая джоба в той же стадии — она идёт параллельно test_backend
test_frontend:
  stage: test
  image: python:3.11-slim
  tags:
    - docker
  before_script:
    - pip install -r frontend/requirements.txt pytest 
  script:
    - echo "Running Frontend tests..."
    # Имитация теста с JUnit отчетом
    - echo '<?xml version="1.0" encoding="utf-8"?><testsuite name="frontend" tests="1" errors="0" failures="0"><testcase classname="frontend.ui" name="test_load"/></testsuite>' > report-frontend.xml
  artifacts:
    reports:
      junit: report-frontend.xml
    expire_in: 1 day

# ---------------------------------------------------------
# 2. Сборка Docker-образов
# ---------------------------------------------------------
build_images:
  stage: build
  tags:
    - docker
  image: docker:latest
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - docker build -t $CI_REGISTRY_IMAGE/backend:$DOCKER_TAG ./backend
    - docker build -t $CI_REGISTRY_IMAGE/frontend:$DOCKER_TAG ./frontend
    - docker push $CI_REGISTRY_IMAGE/backend:$DOCKER_TAG
    - docker push $CI_REGISTRY_IMAGE/frontend:$DOCKER_TAG
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_MERGE_REQUEST_IID

# ---------------------------------------------------------
# 3. Деплой (Staging, Review Apps и Production)
# ---------------------------------------------------------
# Джоба выполняется РАННЕРОМ на 10.0.2.6 (тег app-server).
# Каждое окружение получает свой compose-проект (-p) и свой файл, поэтому
# деплой одного окружения больше не пересоздаёт и не удаляет остальные.
.deploy_template: &deploy_template
  stage: deploy
  tags:
    - app-server
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - echo "Deploying to $DEPLOY_ENV (compose project $DEPLOY_PROJECT) on $(hostname)"
    - |
      cat <<EOF > $COMPOSE_FILE
      services:
        db:
          image: postgres:15-alpine
          environment:
            POSTGRES_USER: crm
            POSTGRES_PASSWORD: $DB_PASSWORD
            POSTGRES_DB: crmdb
          healthcheck:
            test: ["CMD-SHELL", "pg_isready -U crm -d crmdb"]
            interval: 5s
            timeout: 5s
            retries: 5
        backend:
          image: $CI_REGISTRY_IMAGE/backend:$DOCKER_TAG
          environment:
            DATABASE_URL: postgresql://crm:$DB_PASSWORD@db:5432/crmdb
          restart: on-failure
          depends_on:
            db:
              condition: service_healthy
        frontend:
          image: $CI_REGISTRY_IMAGE/frontend:$DOCKER_TAG
          environment:
            API_URL: http://backend:8000
          ports:
            - "$DEPLOY_PORT:8000"
          depends_on:
            - backend
      EOF
    - docker compose -p $DEPLOY_PROJECT -f $COMPOSE_FILE down || true
    - docker compose -p $DEPLOY_PROJECT -f $COMPOSE_FILE up -d
  environment:
    name: $DEPLOY_ENV
    url: http://10.0.2.6:$DEPLOY_PORT

deploy_staging:
  <<: *deploy_template
  variables:
    DEPLOY_ENV: staging
    DEPLOY_PORT: 8090
    DEPLOY_PROJECT: mini-crm-staging
    COMPOSE_FILE: docker-compose.staging.yml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# Review App - запускается для Merge Requests
deploy_review:
  <<: *deploy_template
  variables:
    DEPLOY_ENV: review/$CI_MERGE_REQUEST_IID
    # Порт вида 81ХХ: для IID от 1 до 99 получаются порты 811..8199
    DEPLOY_PORT: "81$CI_MERGE_REQUEST_IID"
    DEPLOY_PROJECT: mini-crm-review-$CI_MERGE_REQUEST_IID
    COMPOSE_FILE: docker-compose.review-$CI_MERGE_REQUEST_IID.yml
  environment:
    name: review/$CI_MERGE_REQUEST_IID
    url: http://10.0.2.6:81$CI_MERGE_REQUEST_IID
    on_stop: stop_review
  rules:
    - if: $CI_MERGE_REQUEST_IID

# Остановка Review App.
# ВАЖНО: джоба со action: stop должна идти в стадии не позже, чем деплой
# (документация GitLab), поэтому она объявлена в первой стадии.
stop_review:
  stage: test
  tags:
    - app-server
  variables:
    GIT_STRATEGY: none
    DEPLOY_PROJECT: mini-crm-review-$CI_MERGE_REQUEST_IID
    COMPOSE_FILE: docker-compose.review-$CI_MERGE_REQUEST_IID.yml
  script:
    - docker compose -p $DEPLOY_PROJECT -f $COMPOSE_FILE down || true
    - rm -f $COMPOSE_FILE
  environment:
    name: review/$CI_MERGE_REQUEST_IID
    action: stop
  rules:
    - if: $CI_MERGE_REQUEST_IID
      when: manual
  allow_failure: true

deploy_production:
  <<: *deploy_template
  variables:
    DEPLOY_ENV: production
    DEPLOY_PORT: 80
    DEPLOY_PROJECT: mini-crm-production
    COMPOSE_FILE: docker-compose.production.yml
  environment:
    name: production
    url: http://10.0.2.6
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual

git add .

git push origin main


Перейдите в **CI/CD -> Pipelines**. 
Вы увидите, как запустятся тесты (параллельно!). Перейдите в джобу `test_backend`, в логах вы увидите, что pytest сгенерировал JUnit XML. В интерфейсе GitLab на вкладке **Tests** пайплайна результаты отобразятся в  таблице.

Когда пайплайн дойдет до `deploy_staging`, джоба отработает на раннере, установленном на 10.0.2.6: она скачает образы из реестра, сгенерирует compose-файл и поднимет контейнеры прямо на этом сервере. Проверьте: `http://10.0.2.6:8090`.

Шаг 7. Работаем с ветками и Review Apps

Настало время проверить магию Review Apps. Разработчик хочет добавить новую фичу.

Создадим ветку:

git checkout -b feature/add-status


Изменим `frontend/app.py`, чтобы статус подсвечивался цветом. Найдите строку с `{d['status']}` и замените на:

f"<td style='color:green;'>{d['status']}</td></tr>"

То есть в итоге должно получиться:
rows = "".join(
    f"<tr><td>{d['id']}</td><td>{d['client_name']}</td>"
    f"<td>{d['amount']}</td><td style='color:green;'>{d['status']}</td></tr>"
    for d in deals
)

Отправим ветку:

git add .
git commit -m "Highlight deal status in green"
git push origin feature/add-status


Теперь в GitLab создайте **Merge Request** из `feature/add-status` в `main`.
Как только вы создадите MR, запустится пайплайн, который:
1. Прогонит параллельные тесты.
2. Соберёт новые образы.
3. Задеплоит ваше изменение как **Review App** на отдельный порт вида `81ХХ` (ХХ — номер merge request; для IID 1..99 это 811..8199) и в отдельном compose-проекте `mini-crm-review-N` — на том же сервере 10.0.2.6!

Каждое окружение живёт в своём compose-проекте (`-p mini-crm-staging`, `-p mini-crm-review-N`, `-p mini-crm-production`) и в своём compose-файле, поэтому деплой одного окружения не трогает контейнеры остальных: review-стенды не мешают staging и production.

Во вкладке **Environments** в GitLab вы увидите новое окружение `review/1` (где 1 — номер MR), а в самом Merge Request появится кнопка **View app**, ведущая прямо на ваш изолированный стенд!

Шаг 8. Слияние и очистка

1. Нажмите **Merge** в Merge Request.
2. Код попадёт в `main`, запустится пайплайн `main`, который задеплоит Staging.
3. Окружение Review App останавливается вручную: перейдите в **CI/CD -> Environments**, найдите ваше `review/1` окружение и нажмите кнопку со стопором (**Stop**), либо используйте кнопку `Stop` в самом MR. При этом запустится джоба `stop_review`, привязанная к окружению через `on_stop` (`action: stop`); она выполнится на раннере на 10.0.2.6, погасит контейнеры этой ветки и удалит её compose-файл — **очистка ресурсов!** Автоостановки при мерже у нас нет, но джоба `stop_review` доступна и просто вручную в пайплайне MR (`when: manual`).
4. Артефакты (отчеты JUnit) удалятся автоматически через 1 день (`expire_in: 1 day`), освобождая место на диске GitLab.

Шаг 9. Отправка уведомлений
Теперь добавим в пайплайн email-уведомления о результатах деплоя. Для этого используем Python (он уже есть в проекте) и стандартную библиотеку smtplib — это самый надёжный способ, не требующий установки дополнительных утилит в раннере.

Шаг 1. Настройка переменных в GitLab
Перейдите в проект mini-crm → Settings → CI/CD → Variables → Add variable:

Key		Value					Masked
SMTP_SERVER	mail.netangels.ru			нет
SMTP_PORT	465 или 587	нет
SMTP_USER	alert@iklimarev.ru			нет
SMTP_PASSWORD	пароль от учётной записи		да (маскировать)
ALERT_EMAIL_TO	ваша личная почта			нет
Примечание: Если SMTP использует SSL/TLS, для порта 465 обычно требуется SSL, для 587 – STARTTLS. В скрипте ниже реализована поддержка обоих.
В поле Value для SMTP_PORT укажите только число — 465 или 587 (без пояснений в скобках: значение подставляется в скрипт как есть).

Шаг 2. Python-скрипт для отправки письма
Создайте в корне проекта файл send_email.py:
#!/usr/bin/env python3
import os
import smtplib
import ssl
from email.message import EmailMessage
import sys

def send_email(subject, body, to_email):
    smtp_server = os.getenv('SMTP_SERVER')
    smtp_port = int(os.getenv('SMTP_PORT', '587'))
    smtp_user = os.getenv('SMTP_USER')
    smtp_password = os.getenv('SMTP_PASSWORD')
    from_email = smtp_user   # обычно совпадает с пользователем

    msg = EmailMessage()
    msg.set_content(body)
    msg['Subject'] = subject
    msg['From'] = from_email
    msg['To'] = to_email

    try:
        # Определяем контекст SSL для порта 465, иначе STARTTLS
        if smtp_port == 465:
            with smtplib.SMTP_SSL(smtp_server, smtp_port, context=ssl.create_default_context()) as server:
                server.login(smtp_user, smtp_password)
                server.send_message(msg)
        else:
            with smtplib.SMTP(smtp_server, smtp_port) as server:
                server.starttls(context=ssl.create_default_context())
                server.login(smtp_user, smtp_password)
                server.send_message(msg)
        print(f"Email sent to {to_email}")
        return True
    except Exception as e:
        print(f"Failed to send email: {e}", file=sys.stderr)
        return False

if __name__ == "__main__":
    # Аргументы командной строки: subject, body, to_email (опционально, берём из переменной)
    subject = sys.argv[1] if len(sys.argv) > 1 else "GitLab CI/CD Notification"
    body = sys.argv[2] if len(sys.argv) > 2 else "No details provided."
    to_email = sys.argv[3] if len(sys.argv) > 3 else os.getenv('ALERT_EMAIL_TO')
    if not to_email:
        print("No recipient email provided. Set ALERT_EMAIL_TO variable or pass as argument.", file=sys.stderr)
        sys.exit(1)
    success = send_email(subject, body, to_email)
    sys.exit(0 if success else 1)

Шаг 3. Добавляем джобу notify в .gitlab-ci.yml
Добавим новую стадию notify после deploy и одну джобу, которая отправит письмо после успешного деплоя в staging.

Обновите .gitlab-ci.yml:
stages:
  - test
  - build
  - deploy
  - notify          # новая стадия

# ... остальные джобы (test_backend, test_frontend, build_images, deploy_staging, deploy_review, stop_review, deploy_production)

# Джоба уведомления – запускается после успешного deploy_staging
notify:
  stage: notify
  image: python:3.11-slim
  tags:
    - docker
  script:
    - |
      SUBJECT="[DEPLOYED] ${CI_PROJECT_NAME}: обновлён staging"
      BODY="Новая версия развёрнута.
      Environment: staging
      Commit: ${CI_COMMIT_SHORT_SHA} - ${CI_COMMIT_TITLE}
      Branch: ${CI_COMMIT_BRANCH}
      Pipeline: ${CI_PIPELINE_URL}
      URL: http://10.0.2.6:8090
      "
      python send_email.py "$SUBJECT" "$BODY"
  when: on_success
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  needs:
    - deploy_staging

Почему здесь нет проверки `CI_JOB_STATUS`: эта переменная доступна только в `after_script`, поэтому в `script` она пустая — проверка всегда уходила бы в ветку FAILURE, и письмо приходило бы с неверной темой. Если нужно письмо и при падении пайплайна — сделайте отдельную джобу с `when: on_failure`, а статус пайплайна при необходимости берите через API (как в практике 9).
Шаг 4. Проверка
После коммита и пуша в main, при успешном деплое в staging вы получите письмо на указанный адрес ALERT_EMAIL_TO. Убедитесь, что переменная ALERT_EMAIL_TO заполнена корректно.
